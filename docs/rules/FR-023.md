# Object reads are audit logged

| | |
|---|---|
| **ID** | FR-023 |
| **Severity** | medium |
| **STRIDE** | Repudiation |
| **Category** | Logging |
| **Platforms** | AWS, Google Cloud, Cloudflare |

Available since Fray's first public release

## The risk

Object reads leave no audit trail

## Why it matters

Without a data-access audit log, a read of an object cannot be attributed to a caller after the fact.

## How Fray evaluates it

| Result | Meaning |
|---|---|
| **Open** | Object reads are not audit logged. |
| **Mitigated** | Object reads are audit logged. |
| **Unverified** | Fray could not tell whether object reads are audit logged. On Cloudflare R2, Data Access Logs are enabled per bucket in the dashboard and are not visible in Terraform, so R2 buckets are reported as unverified. For S3 and Cloud Storage, a missing logging configuration is reported as open only when `audit_config: owned_by_this_root` is set. |

## How to fix

Record data-read access on the bucket.

- **Cloudflare** (`cloudflare_r2_bucket`): Enable Data Access Logs in the bucket settings. They are retained for seven days; export them if you need longer retention.

## Waiving it

Add an entry to `.fray/waivers.yml`. Field limits and expiry horizons are in [Waivers](https://github.com/fluong/fray#waivers).
`address` is a Terraform resource address for an element finding, or `<from> -> <to> <data_class>` for a flow finding.

```yaml
version: 1
waivers:
  - id: waiver-1
    rule: FR-023
    address: aws_s3_bucket.uploads
    reason: "Accepted risk; reviewed with the owning team."
    owner: "@security-eng"
    expires: "YYYY-MM-DD"
```
