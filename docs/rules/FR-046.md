# Workload cannot administer the database through the cloud API

| | |
|---|---|
| **ID** | FR-046 |
| **Severity** | medium |
| **STRIDE** | Tampering, Elevation of privilege, Denial of service |
| **Category** | Identity |
| **Platforms** | AWS, Google Cloud |

Requires Action v0.35.0 or later.

Severity is **high** when the grant applies account-wide (or project-wide on Google Cloud). Severity is **medium** when the grant applies to one database instance or cluster only.

## The risk

Workload can administer the database through the cloud API

## Why it matters

Application roles should normally use data-plane access (connect and query). Control-plane API rights let the workload change master passwords, copy or share snapshots, restore clones, or delete the database — without using SQL on the wire. That bypasses application-layer controls and can lead to credential takeover, data exfiltration, or destruction.

Fray classifies control-plane rights into four kinds when they appear on a flow from compute into a relational database:

| Class | What it means in practice |
|---|---|
| **reset_credentials** | Reset the master or admin password through the cloud API. |
| **snapshot_exfiltrate** | Create, copy, share, or export snapshots (including to object storage). |
| **restore_clone** | Restore from a snapshot or point in time into a new instance the caller can reach. |
| **delete** | Delete the database or its snapshots through the cloud API. |

## How Fray evaluates it

Fray evaluates this rule only on flows from compute into a relational database when control-plane classes are present on the flow. Flows with no known control-plane grant do not produce a finding for this rule.

| Result | Meaning |
|---|---|
| **Open** | The workload has one or more of the control-plane classes on this flow. |
| **Mitigated** | Not reported: Fray only flags flows where control-plane rights are present. |
| **Unverified** | Fray could not tell whether control-plane rights are present (for example the IAM policy JSON was unknown at plan time). |

## How to fix

Remove control-plane actions from application task roles. Use break-glass or automation roles with narrow resource ARNs, and scope `rds:*` (or Cloud SQL admin) away from production application identities.

- **AWS** (`aws_iam_role_policy`, `aws_iam_policy`): Drop `rds:ModifyDBInstance`, snapshot, restore, and delete actions from the app task role; keep `rds-db:connect` scoped to the instance user ARN where IAM database authentication is used.
- **Google Cloud** (`google_project_iam_member`): Do not grant `roles/cloudsql.admin` to the Cloud Run or GCE service account; use `roles/cloudsql.client` / instance user instead.

## Waiving it

Add an entry to `.fray/waivers.yml`. Field limits and expiry horizons are in [Waivers](https://github.com/fluong/fray#waivers).
`address` is a Terraform resource address for an element finding, or `<from> -> <to> <data_class>` for a flow finding.

```yaml
version: 1
waivers:
  - id: waiver-1
    rule: FR-046
    address: aws_ecs_service.app -> aws_db_instance.main unknown
    reason: "Accepted risk; reviewed with the owning team."
    owner: "@security-eng"
    expires: "YYYY-MM-DD"
```
