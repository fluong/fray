# Audit archive is tamper-evident

| | |
|---|---|
| **ID** | FR-027 |
| **Severity** | medium |
| **STRIDE** | Tampering |
| **Category** | Logging |
| **Platforms** | AWS, Google Cloud, Cloudflare |

Available since Fray's first public release

## The risk

Audit archive objects can be overwritten or deleted

## Why it matters

An audit archive that a principal can write is only trustworthy when objects cannot be altered or deleted (object lock / retention lock). When immutability is unknown the finding stays unverified and never gates. Public inbound writes are included: no other rule covers public writes into an audit archive (FR-010 covers public read exposure; FR-001 only credentials flows).

## How Fray evaluates it

| Result | Meaning |
|---|---|
| **Open** | Audit-archive objects can be overwritten or deleted. |
| **Mitigated** | Audit-archive objects are immutable (tamper-evident retention). |
| **Unverified** | Fray could not tell whether audit-archive objects are immutable. |

## How to fix

Enable object lock (COMPLIANCE mode) or a locked retention policy on the audit archive.

## Waiving it

Add an entry to `.fray/waivers.yml`. Field limits and expiry horizons are in [Waivers](https://github.com/fluong/fray#waivers).
`address` is a Terraform resource address for an element finding, or `<from> -> <to> <data_class>` for a flow finding.

```yaml
version: 1
waivers:
  - id: waiver-1
    rule: FR-027
    address: aws_s3_bucket.assets
    reason: "Accepted risk; reviewed with the owning team."
    owner: "@security-eng"
    expires: "YYYY-MM-DD"
```
