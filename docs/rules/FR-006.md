# Secret reads are audit logged

| | |
|---|---|
| **ID** | FR-006 |
| **Severity** | low |
| **STRIDE** | Repudiation |
| **Category** | Logging |
| **Platforms** | AWS, Google Cloud |

Available since Fray's first public release

## The risk

Secret reads leave no audit trail

## Why it matters

Without a data-access audit log, a secret read cannot be attributed to a caller after the fact.

## How Fray evaluates it

| Result | Meaning |
|---|---|
| **Open** | Reads of the secret are not audit logged. |
| **Mitigated** | Secret reads are audit logged. On AWS, CloudTrail records Secrets Manager API calls, including secret reads, by default; the last 90 days are visible in CloudTrail Event history per Region without a trail. Fray therefore treats Secrets Manager access as logged. To keep records longer than 90 days, configure a CloudTrail trail. |
| **Unverified** | Fray could not tell whether secret reads are audit logged. |

## How to fix

Record data-read and data-write access on the secret store.

- **Google Cloud** (`google_secret_manager_secret`): On Google Cloud, enable Data Access audit logs (DATA_READ) for secretmanager.googleapis.com or allServices, at project, folder or organization level. Fray counts any such configuration present in the plan; when none is present, the finding is open only if `audit_config: owned_by_this_root` is set, otherwise unverified.

## Waiving it

Add an entry to `.fray/waivers.yml`. Field limits and expiry horizons are in [Waivers](https://github.com/fluong/fray#waivers).
`address` is a Terraform resource address for an element finding, or `<from> -> <to> <data_class>` for a flow finding.

```yaml
version: 1
waivers:
  - id: waiver-1
    rule: FR-006
    address: aws_secretsmanager_secret.db
    reason: "Accepted risk; reviewed with the owning team."
    owner: "@security-eng"
    expires: "YYYY-MM-DD"
```
