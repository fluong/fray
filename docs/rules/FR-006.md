# Secret reads are audit logged

| | |
|---|---|
| **ID** | FR-006 |
| **Severity** | low |
| **STRIDE** | Repudiation |
| **Category** | Logging |
| **Platforms** | AWS, Google Cloud |

Available since Fray's first public release

## The risk

Secret reads leave no audit trail

## Why it matters

Without a data-access audit log, a secret read cannot be attributed to a caller after the fact.

## How Fray evaluates it

| Result | Meaning |
|---|---|
| **Open** | Reads of the secret are not audit logged. |
| **Mitigated** | Secret reads are audit logged. |
| **Unverified** | Fray could not tell whether secret reads are audit logged. |

## How to fix

Record data-read and data-write access on the secret store.

## Waiving it

Add an entry to `.fray/waivers.yml`. Field limits and expiry horizons are in [Waivers](https://github.com/fluong/fray#waivers).
`address` is a Terraform resource address for an element finding, or `<from> -> <to> <data_class>` for a flow finding.

```yaml
version: 1
waivers:
  - id: waiver-1
    rule: FR-006
    address: aws_s3_bucket.assets
    reason: "Accepted risk; reviewed with the owning team."
    owner: "@security-eng"
    expires: "YYYY-MM-DD"
```
